# Стенд этапа 8: несколько валидаторов v2 на Malachite (Tendermint BFT)

Проверка того, как цепочку v2 выпускают несколько валидаторов вместо одного
производителя. Стенд **не входит** в workspace: у него свой `Cargo.toml` с
пустым `[workspace]` и свой `Cargo.lock`. Протокол v1 и форматы кошельков не
менялись.

По итогам стенда консенсус встроен в `orvexa-shielded` (`src/bft`, §6.7
[спецификации](../../docs/PRIVATE_V2_SPEC.md)); там же тест на четырёх
процессах-валидаторах `tests/bft_network.rs`.

## Движок

[Malachite](https://github.com/circlefin/malachite): `arc-malachitebft-core-consensus`
0.8.1 (Circle, Apache-2.0). Это реализация Tendermint на Rust в виде
детерминированного конечного автомата без сети и ввода-вывода: хост сам
подписывает, проверяет, ведёт таймеры, журнал (WAL) и рассылку. Поэтому его
можно вшить в `orvexa-shielded` и в ORVEXA Desktop без отдельного процесса.

**Оговорка.** Malachite помечен как alpha и не проходил внешний аудит (есть
формальная спецификация на Quint и собственные тесты проекта). Для тестовой
сети это приемлемо. Перед реальными средствами нужен внешний аудит этого
движка или переход на проверенный (CometBFT).

## Что сделано

- `src/ctx.rs` — контекст ORVEXA. Консенсус договаривается о 32-байтном id
  блока (`ProposalAndParts`): тело блока предлагающий рассылает отдельно,
  каждый валидатор сам проверяет его по правилам приложения и только затем
  сообщает консенсусу «допустим / недопустим». Голоса и предложения
  подписываются Ed25519 по фиксированной раскладке байтов с доменами
  `ORVEXA/bft-vote/v1`, `ORVEXA/bft-proposal/v1` и chain ID; chain ID включает
  набор валидаторов и их веса. Расширения голосов отключены и отвергаются.
- `src/sim.rs` — детерминированный симулятор с виртуальным временем. Каждый
  валидатор — неизменённый автомат Malachite. Один seed задаёт всё, поэтому
  любой сбой воспроизводится точно.
  - Сеть: задержка, потери, разделения на группы.
  - Аварии: теряется всё, кроме цепочки, WAL текущей высоты, полученных тел
    блоков и своих предложений. Перезапуск воспроизводит WAL.
  - Догоняющий валидатор просит у соседей пары «блок + сертификат коммита» и
    принимает пару, только если сертификат (> 2/3 веса) проверяется по набору
    валидаторов. Соседа, приславшего подделку, больше не спрашивает.
  - Византийские валидаторы: двойные предложения и противоречивые голоса
    разным половинам сети, недопустимые блоки, поддельные ответы догоняющим.
  - Наблюдатель записывает каждое решение и каждый голос честных валидаторов.
- `tests/scenarios.rs` — сценарии отказов. В конце каждого проверяется
  безопасность: на каждой высоте у всех честных один и тот же блок, цепочки
  связаны, каждый сертификат проверяется, нет недопустимых блоков, нет
  двойных голосов честных, включая перезапуски.

## Сценарии и результат

19 тестов, все проходят (`cargo test`, ≈ 4 с), плюс 2000 seed смешанных
отказов (`BFT_SEEDS=2000 cargo test --release -- --ignored`, ≈ 1 мин). Apple
M4, rustc 1.99.1.

Самопроверка наблюдателя — без неё зелёные тесты ничего бы не значили:

- валидаторы, настроенные на кворум 1/3, при разделении 2 / 2 создают форк, и
  проверка его находит;
- валидаторы, которые при перезапуске забывают WAL, голосуют повторно иначе,
  и проверка находит двойной голос честного.

## Что нашли

Seed 381 из длинного прогона: после перезапуска Malachite остановил валидатор
с `ReplayDivergence` (пересчитанный голос не совпал с журналом — это его
защита от двойной подписи). Причина была в хосте: таймаут уже
зафиксированной высоты приходил после фиксации, попадал в журнал следующей
высоты и при воспроизведении читался как её таймаут. WAL теперь хранится с
высотой каждой записи, и записи старых высот отбрасываются. Для встраивания в
`orvexa-shielded` это обязательное правило.

Другие требования к хосту, которые подтвердил стенд:

- запись в WAL должна быть на диске раньше, чем голос уйдёт в сеть;
- после перезапуска на ту же (высоту, раунд) надо предложить тот же блок, что
  и до аварии, — поэтому свои предложения хранятся на диске;
- тела блоков текущей высоты тоже хранятся на диске, иначе после перезапуска
  нельзя довести решение до блока.

## Ограничения стенда

- Сеть смоделирована: отправитель сообщения известен, тела блоков не
  подписаны (подменить их нельзя только потому, что консенсус решает по id из
  подписанного предложения). В настоящей сети нужны подписанные или
  аутентифицированные каналы.
- Набор валидаторов постоянный, веса равные; смены набора и наказаний нет.
- Время виртуальное: скорость в миллисекундах — свойство модели, а не
  измерение. В исправной сети 4 валидатора делают ≈ 40 сообщений на блок.
- Тело блока — заглушка; транзакции v2 не проверяются (это делает
  `orvexa-shielded`).

## Запуск

```bash
cd research/bft-eval
cargo test --locked
BFT_SEEDS=2000 cargo test --release --locked -- --ignored
```

Отладка одного seed: `BFT_DEBUG=1` печатает WAL при каждом перезапуске.
