# Операторы приватной тестовой сети v2

Как поднять общую тестовую сеть v2 с несколькими валидаторами, к которой люди
подключаются из ORVEXA Desktop одной кнопкой. Это тестовая сеть: монеты не
имеют ценности.

Блоки решают валидаторы консенсусом BFT (§6.7
[спецификации](PRIVATE_V2_SPEC.md)): блок принят, когда его подписали больше
2/3 валидаторов. Ни один валидатор в одиночку не может подделать блок, потратить
чужие средства или создать атомы сверх эмиссии. При 4 валидаторах сеть
работает, пока включены любые 3; при 7 — любые 5. Если включено меньше, сеть
стоит, но не расходится, и продолжает работу, когда валидаторы вернутся.

| Валидаторов | Нужно на связи | Может отказать или вести себя нечестно |
|---|---|---|
| 1 | 1 | 0 |
| 4 | 3 | 1 |
| 7 | 5 | 2 |
| 10 | 7 | 3 |

Движок консенсуса (Malachite) не проходил внешний аудит — для тестовой сети это
допустимо, для реальных средств нет.

## Быстрый путь: сеть на своём Mac

Один валидатор на этом Mac, в фоне (launchd), пока Mac включён — даже с
закрытым приложением. Блоки решает один компьютер: для проверки «одной
кнопки» этого хватает, для настоящей сети нет.

```bash
bash scripts/v2-validator-macos.sh create --to <ovxt1… адрес вашего кошелька v2> --url https://v2.<ваш-домен>
bash scripts/v2-validator-macos.sh tunnel-help   # как вывести узел наружу через cloudflared
bash scripts/v2-validator-macos.sh start
bash scripts/v2-validator-macos.sh publish       # подписывает docs/networks/directory.json ключом выпуска
```

После коммита `docs/networks/` в `main` GitHub Pages публикует список, и в
приложении у всех работает кнопка «Подключиться к сети ORVEXA v2». Ключи и
цепочка лежат в `~/Library/Application Support/ORVEXA v2 validator`
(`validator.key` — сделайте копию и никому не передавайте). `status`, `logs`,
`stop`, `set-url` — для обслуживания; адрес можно поменять без новой сети,
затем снова `publish`.

## Что нужно каждому валидатору

- Сервер с постоянным адресом и временем работы: VPS за несколько долларов в
  месяц или домашний компьютер, который не выключается.
- Домен и HTTPS перед узлом (например, Caddy). Через этот адрес другие
  валидаторы шлют сообщения консенсуса (`/v2/consensus`), а участники берут блоки.
- Резервная копия своего ключа валидатора. Ключ никому не передаётся.

## 1. Каждый валидатор создаёт ключ

```bash
cargo build --release --locked -p orvexa-shielded
./target/release/orvexa-v2-node keygen --out validator.key
```

Команда печатает открытый ключ (64 hex-символа). Его вместе с адресом своего
узла валидатор отправляет координатору. `validator.key` создаётся с правами
0600 и никогда не перезаписывается.

## 2. Координатор создаёт сеть

```bash
./target/release/orvexa-v2-node genesis \
  --to <ovxt1… адрес кошелька, который получит тестовую эмиссию> \
  --validators <ключ1>@https://v1.example.org,<ключ2>@https://v2.example.org,<ключ3>@https://v3.example.org,<ключ4>@https://v4.example.org \
  --name "ORVEXA v2 test" \
  --nodes https://v1.example.org \
  --out network.json
```

`network.json` — публичный файл сети; его получают все валидаторы и участники.
Ключи валидаторов входят в chain ID: изменить набор — значит создать новую
сеть. Адреса можно поменять позже, не меняя сеть.

Сеть на одном компьютере (один валидатор): вместо `--validators` укажите
`--validator-key validator.key`.

## 3. Каждый валидатор запускает узел

```bash
./target/release/orvexa-v2-node run --data-dir /var/lib/orvexa-v2 \
  --network network.json --validator-key validator.key \
  --listen 127.0.0.1:4260
```

Caddy (`/etc/caddy/Caddyfile`):

```text
v1.example.org {
    reverse_proxy 127.0.0.1:4260
}
```

Узел слушает только localhost, наружу открыт лишь порт 443 прокси. Обозреватель
доступен по `https://v1.example.org/`. Запускайте как службу (`systemd`,
`Restart=always`, пользователь без прав администратора).

В каталоге данных две базы: `v2.sqlite` (цепочка) и `consensus.sqlite` (журнал
консенсуса). Обе переживают аварийную остановку: после перезапуска валидатор
продолжает начатую высоту с того места, где остановился, и забирает у соседей
блоки, принятые без него. **Не копируйте каталог данных и ключ на второй
компьютер, пока работает первый**: два узла с одним ключом могут
проголосовать по-разному, а это и есть нечестное поведение.

Необязательные параметры: `--block-every-ms` (пауза между блоками, по
умолчанию 1000), `--timeouts-ms` (таймаут предложения, по умолчанию 1500;
остальные таймауты масштабируются).

## 4. Дополнительные публичные узлы (необязательно)

Любой может держать ведомый узел: он проверяет сертификат и доказательства
каждого блока и отдаёт те же данные.

```bash
./target/release/orvexa-v2-node run --data-dir v2-follower --network network.json \
  --follow https://v1.example.org --listen 127.0.0.1:4261
```

Его адрес можно добавить в `nodes` профиля. Chain ID от этого не меняется.

## 5. Как люди подключаются

- **Одной кнопкой:** подпишите список сетей (`orvexa-v2-node directory` или
  `scripts/v2-validator-macos.sh publish`) и закоммитьте `docs/networks/` в
  `main`. Приложение найдёт сеть по кнопке «Подключиться к сети ORVEXA v2» без
  нового выпуска и без файлов (§6.6.1 [спецификации](PRIVATE_V2_SPEC.md)).
- **Файлом:** раздайте `network.json`; в приложении «Загрузить файл сети».

## Ограничения

- Набор валидаторов постоянный, голоса равные, наград и наказаний нет.
- Перевод, который ждёт в очереди, теряется, если одновременно выключились все
  валидаторы; кошелёк отправляет его снова.
- Узлы участников не принимают входящих соединений и не раздают блоки другим.
- IP-адреса участников видны серверу, к которому они подключены.
