# Спецификация приватной ORVEXA v2 — черновик для review

Статус: **черновик**, этап 3 плана. Правила ниже реализованы в
[crates/orvexa-shielded](../crates/orvexa-shielded/) и включены в ORVEXA
Desktop как **отдельная локальная тестовая сеть** (§6.5). Узел v1 от крейта не зависит. Протокол v1, его форматы и `Cargo.lock` не меняются. Тестовые
атомы v1 автоматически не переходят в v2.

Основа: [дизайн приватности](PRIVACY_DESIGN.md), разделы 4, 5 и 8;
[план тестов](PRIVACY_TEST_PLAN.md), P2/P3; [стенд P1](../research/orchard-eval/README.md).

## 1. Криптографический набор (suite 1)

| Параметр | Значение |
|---|---|
| Библиотека | `orchard = "=0.16.0"` (`std`, `circuit`, `multicore`), MIT OR Apache-2.0 |
| Bundle | `BundleVersion::ironwood_v3()` |
| Circuit | `OrchardCircuitVersion::PostNu6_3`; verifying key строится узлом и никогда не берётся из входа |
| Commitment bundle | `Bundle::commitment(TxVersion::V6)` (BLAKE2b-256 upstream) |
| Note encryption | `IronwoodDomain`, note plaintext V3 |
| Пакетная проверка | `BatchValidator`: proof, все SpendAuth-подписи и binding-подпись |

Номер «v2» относится к ORVEXA и не означает совместимость с транзакциями Zcash.

## 2. Конверт транзакции

Канонический бинарный формат. Целые числа — little-endian фиксированной ширины.
Точки и поля — канонические кодировки upstream (`from_bytes`). Длина proof не
передаётся: она равна `Proof::expected_proof_size(n) = 2720 + 2272·n`.
Лишние байты после конца запрещены, поэтому одному конверту соответствует ровно
одна строка байтов.

| Поле | Байты | Правило |
|---|---|---|
| magic | 4 | `OVX2` |
| version | 1 | `2` |
| suite | 1 | `1` |
| chain_id | 32 | см. §5 |
| fee | 8 | u64 |
| expiry_height | 8 | u64 |
| n_actions | 1 | `1..=16` |
| actions × n | 884 каждый | `cv_net 32 · nf 32 · rk 32 · cmx 32 · epk 32 · enc_ciphertext 580 · out_ciphertext 80 · spend_auth_sig 64` |
| flags | 1 | `Flags::from_byte` для ironwood_v3; зарезервированные биты = 0 |
| value_balance | 8 | i64 |
| anchor | 32 | корень дерева commitments |
| proof | 2720 + 2272·n | Halo2 |
| binding_sig | 64 | RedPallas |

Размер: 55 + 884·n + 105 + (2720 + 2272·n). Для 2 / 4 / 8 actions это
9 192 / 15 504 / 28 128 байт.

Декодер:
1. Отвергает вход длиннее максимального конверта (16 actions) до любого разбора.
2. Проверяет magic, version, suite, n_actions.
3. Отвергает неточную длину (`Truncated` / `TrailingBytes`) до декодирования точек.
4. Декодирует точки; `Action::from_parts` отвергает identity `rk` и
   недопустимый `epk`. Затем `Bundle::try_from_parts` проверяет flags и
   каноническую длину proof.

## 3. Sighash и идентификатор транзакции

```text
sighash = SHA-256( "ORVEXA/shielded-sighash/v2"
                 ‖ version ‖ suite ‖ chain_id ‖ fee ‖ expiry_height
                 ‖ n_actions ‖ flags_byte ‖ anchor
                 ‖ Bundle::commitment(TxVersion::V6) )

txid    = SHA-256( "ORVEXA/shielded-txid/v2" ‖ весь конверт )
```

Commitment v6 охватывает все эффекты bundle: actions с ciphertexts,
`value_balance` и flags. Anchor в эффекты v6 не входит, поэтому добавлен явно.
Proof и подписи в sighash не входят, иначе возникает цикл. Txid охватывает
каждый байт конверта, включая их.

## 4. Правила обычной транзакции

Проверки идут в таком порядке. Первая ошибка отвергает **весь блок**.

| # | Правило | Ошибка |
|---|---|---|
| 1 | Канонический конверт (§2) | `Envelope(..)` |
| 2 | `chain_id` совпадает с сетью | `WrongChain` |
| 3 | `height ≤ expiry_height ≤ height + max_expiry_delta` | `Expired` / `ExpiryTooFar` |
| 4 | flags = `ironwood_v3().default_flags()`: spends, outputs и cross-address включены | `Flags` |
| 5 | `fee ≥ 1` | `FeeBelowMinimum` |
| 6 | `value_balance == fee` (через `i64::try_from`) | `ValueBalanceNotFee` |
| 7 | anchor равен корню дерева после одного из последних `anchor_window` блоков | `UnknownAnchor` |
| 8 | Ни один nullifier не встречался в цепочке | `NullifierAlreadySpent` |
| 9 | Nullifiers уникальны внутри bundle и внутри блока | `DuplicateNullifier` |
| 10 | Сумма комиссий блока ≤ остатку эмиссии (checked) | `FeeExceedsRemainingSupply` |
| 11 | Одна пакетная проверка всех proof и подписей блока | `Authorization` |

Правила 6 и 4 закрывают то, что библиотека принимает сама по себе (стенд P1):
отрицательный value balance — вход стоимости в пул из ниоткуда, и bundle с
выключенными spends — mint. Правила 8–9 закрывают повтор nullifier: библиотека
проверяет один bundle и о состоянии цепочки не знает.

Комиссия публична и сжигается. Остаток эмиссии = `supply − Σ fees`. Открытые
балансы для этого не суммируются.

## 5. Genesis и chain ID

Genesis — единственный bundle с выключенными spends (`Flags::SPENDS_DISABLED`).
Его условия: `fee = 0`, `expiry_height = 0`, `value_balance = −supply`,
anchor равен корню пустого дерева.

```text
chain_id = SHA-256( "ORVEXA/chain-id/v2" ‖ version ‖ suite ‖ salt ‖ supply
                  ‖ anchor_window ‖ max_expiry_delta
                  ‖ число валидаторов u32 ‖ ключи валидаторов (по возрастанию) ‖ genesis_anchor
                  ‖ Bundle::commitment(TxVersion::V6) неподписанного genesis )
```

Эффекты не зависят от подписей. Поэтому genesis подписывается уже под
вычисленным `chain_id`, и цикла нет. Узел пересчитывает `chain_id` из
конфигурации и принятого genesis. Другая соль, эмиссия, выходы или набор
валидаторов дают другую сеть.

После genesis bundle с выключенными spends не принимается никогда (правило 4).

## 6. Блок и состояние

```text
block_id  = SHA-256( "ORVEXA/shielded-block/v2" ‖ chain_id ‖ height ‖ prev
                   ‖ число транзакций ‖ txid… )
precommit = "ORVEXA/shielded-vote/v2\n" ‖ chain_id ‖ 0x01 ‖ height (u64 BE)
            ‖ round (i64 BE) ‖ 0x01 ‖ block_id ‖ ключ валидатора
commit    = round u32 ‖ [(ключ валидатора, Ed25519(precommit))…]
```

Каждый блок после genesis несёт **сертификат коммита**: подписи precommit
больше 2/3 валидаторов сети (`validators` в параметрах, 1–64 ключа, по одному
голосу, входят в chain ID) за этот block ID на этой высоте в одном раунде.
Это ровно те голоса, которые валидаторы подписывают в консенсусе (§6.7), поэтому
сертификат проверяется без движка консенсуса: ведомый узел и кошелёк никому
не доверяют на слово. Узел проверяет сертификат (`verify_strict`, каждый
подписант — валидатор и встречается один раз, подписантов ≥ ⌊2n/3⌋ + 1) до
проверки транзакций, при каждом приёме и при каждом повторном чтении базы.
Сертификат не входит в block ID. Подписи постороннего, повтор одного
валидатора, недобор, другой раунд, другая сеть или изменённое после голосования
содержимое — `BadCommit`.

Кодирование блока: height u64 · prev 32 · round u32 · число подписей u16 ·
(ключ 32 · подпись 64)… · число транзакций u32 · (длина u32 · конверт)….

Состояние: дерево commitments глубины 32 (`MerkleHashOrchard`, `shardtree`),
корни последних `anchor_window` блоков, множество nullifiers, сожжённые
комиссии, высота и tip. Блок применяется целиком или не применяется: все
проверки выполняются до первого изменения. Состояние восстанавливается повтором
genesis и блоков. Одинаковый `state_digest` означает одинаковое состояние.

Nullifiers фиктивных (dummy) actions записываются так же, как остальные.
Обхода через dummy нет (P3-13).

### 6.1. Хранение

SQLite (`synchronous=FULL`, эксклюзивная блокировка, как у узла v1).
Таблицы: `meta` (параметры, genesis, tip, высота, сожжённое), `blocks`
(тело блока), `nullifiers` (PRIMARY KEY — повтор невозможен и на уровне БД),
`commitments` (позиция → cmx), `roots`.

Применение блока:
1. Блок проходит все правила без изменения состояния. Новый корень
   вычисляется на копии frontier.
2. Тело блока, nullifiers, commitments, корень и tip записываются **одной**
   SQL-транзакцией.
3. Только после COMMIT меняется состояние в памяти.

При открытии состояние пересчитывается из genesis и тел блоков, с проверкой
цепочки block ID. Таблицы nullifiers, commitments, roots и метаданные
сравниваются с пересчётом; любое расхождение — `Corrupt`. Режим `Verify`
заново проверяет все доказательства. Режим `Skip` доверяет доказательствам,
которые узел сам проверил перед записью, но каждый байт блока по-прежнему
связан через block ID.

## 6.2. Кошелёк с seed-фразой (этап 5)

| Шаг | Правило |
|---|---|
| Мнемоника | BIP39, английский словарь, **24 слова** (256 бит энтропии ОС); библиотека `bip0039 = "=0.14.2"` (Apache-2.0), проверена официальными векторами Trezor |
| Seed | BIP39 PBKDF2-HMAC-SHA512, пустая passphrase → 64 байта |
| Ключ | ZIP 32 Orchard: `SpendingKey::from_zip32_seed(seed, coin_type, account)` |
| coin_type | `1` (SLIP-44 «Testnet, all coins») — **временно**; до любой нетестовой сети нужен собственный |
| Адреса | внешние: diversifier 0, 1, 2… (несвязываемые); сдача — внутренний адрес (`Scope::Internal`) |
| Обнаружение | пробная расшифровка каждого output внешним и внутренним IVK (`IronwoodDomain`) |
| Witness | собственное дерево кошелька: все commitments, помечены только свои notes; anchor = корень этого дерева, у узла дерево не запрашивается |
| Ожидающие траты | выбранные notes зарезервированы до появления nullifier в цепочке или до истечения `expiry_height`, затем снова доступны |

Восстановление: фраза → ключи → пересканирование цепочки с genesis даёт те же
notes (включая сдачу), те же потраченные nullifiers и тот же баланс. Старые
случайные ключи v1 этим не восстанавливаются, им нужен их собственный файл.

**Файл кошелька** `orvexa-seed-wallet`, версия 2. Конструкция та же, что у v1:
Argon2id (64 МиБ, 3 прохода, 1 поток) → XChaCha20-Poly1305. Открытые метаданные
(сеть, coin type, аккаунт, birthday, параметры KDF, соль, nonce) аутентифицированы
как AAD. Шифруется только 32-байтная энтропия; notes всегда пересчитываются
сканированием. Пароль не короче 12 символов. Запись: временный файл (0600) →
fsync → жёсткая ссылка на итоговое имя → fsync каталога. Существующий файл
никогда не заменяется, авария оставляет либо ничего, либо полный файл.

## 6.3. Управление приватностью (этап 6)

Обычный перевод всегда приватный. Ошибка приватного перевода возвращает ошибку
и ничего не раскрывает: обходного публичного пути в коде нет.

**Квитанция одного платежа** (`orvexa-receipt-v2:` + hex + 4 байта
SHA-256-контрольной суммы, 153 байта данных): chain ID, txid, номер action,
адрес получателя (43 байта), сумма, `rseed`. Проверяющий:
1. сверяет сеть и txid переданной транзакции;
2. убеждается, что txid включён в цепочку;
3. берёт `rho` из самого action;
4. собирает note (`NoteVersion::V3`) и сравнивает её commitment с `cmx`.

Commitment связывающий, поэтому сумму и получателя нельзя исказить. Квитанцию
может сделать получатель (из своей note) или отправитель: его исходящие
платежи восстанавливаются через OVK. Квитанция **не** раскрывает отправителя,
сдачу, другие выходы, баланс и ключи. После передачи её нельзя отозвать.

**Ключи только для просмотра:**

| Ключ | Текстовый вид | Видит | Не видит |
|---|---|---|---|
| полный (FVK, 96 байт) | `orvexa-fvk-v2:…` | входящие, исходящие (OVK), сдачу, траты, точный баланс | — (тратить не может) |
| только входящие (IVK, 64 байта) | `orvexa-ivk-v2:…` | платежи на внешние адреса: суммы и время | сдачу, траты, исходящие, баланс |

Обе формы с контрольной суммой. Перед экспортом кошелёк показывает охват
ключа простым языком (`scope_ru`). Ключ раскрывает и прошлую, и будущую
историю; отозвать скопированный ключ нельзя. Кошелёк с ключом просмотра не
тратит, не имеет фразы и не создаёт файл seed.

**Публичный платёж** — тот же приватный перевод плюс квитанция для публикации.
Он требует согласия `PublicConsent { to, amount }`, совпадающего с переводом.
Экран подтверждения перечисляет, что станет публичным (адрес получателя, сумма,
txid) и что останется скрытым (отправитель, сдача, остальные платежи). При
расхождении перевод не строится. Отдельного прозрачного пула в v2 нет.

## 6.4. Локальный узел v2, API и обозреватель (этап 7)

`orvexa-v2-node` (в прототипе) — состояние в `Store` (§6.1), мемпул и JSON-API
на localhost. Две роли:

- **валидатор** — вместе с остальными валидаторами решает блоки консенсусом
  BFT (§6.7); каждый блок проходит все правила §4 у каждого валидатора;
- **ведомый** — забирает блоки у узла по HTTP, перепроверяет каждый
  (сертификат коммита и доказательства) и сохраняет; присланные транзакции
  пересылает этому узлу.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/v2/status` | сеть, роль, chain ID, высота, tip, сожжённые комиссии, остаток эмиссии, размер мемпула |
| GET | `/v2/blocks?from=&limit=` | последние блоки (до 50): хеш, родитель, подтверждения, txid, число actions, комиссии |
| GET | `/v2/blocks/{h}` и `/raw` | один блок; `raw` — тело для скана кошельком и для ведомых узлов |
| GET | `/v2/tx/{txid}` и `/raw` | высота или «ожидает», подтверждения, комиссия, expiry, actions, размер, nullifiers, commitments |
| GET | `/v2/genesis/raw` | genesis |
| POST | `/v2/tx` | `{tx: hex}` → 202 `{txid}`; 409 при повторе nullifier или конфликте в мемпуле, 400 при нарушении правил |
| POST | `/v2/consensus` | двоичное сообщение консенсуса от другого валидатора (§6.7); у ведомого — 404 |
| GET | `/` | страница обозревателя (русский) |

В ответах нет ни одного адреса, суммы, memo, ключа или открытого текста note.
Кошелёк скачивает блоки целиком и сканирует их сам; на узел не отправляются ни
ключи, ни адреса. Клиент проверяет, что txid ответа совпадает с запрошенным.
Мемпул отвергает вторую транзакцию, тратящую ту же note, и не переживает
перезапуск: потерянная транзакция истекает, и кошелёк освобождает её notes.
Логи содержат только высоты, txid и коды ошибок.

## 6.5. ORVEXA Desktop: отдельная тестовая сеть v2

Раздел «Приватная сеть v2» в приложении. Кошелёк v1 и его сеть не меняются:
в контроллер v1 добавлена только точка подключения дополнительных маршрутов
(`router_with`) под тем же guard loopback Host/Origin.

**Где ключи.** В отличие от v1, где подпись делает браузер (Wasm), кошелёк v2
работает в нативном процессе приложения: доказательства Halo2 слишком тяжелы
для страницы. Ключи всё равно не покидают устройство:

- seed хранится только в зашифрованном файле (§6.2) в `<данные>/v2/wallets`
  (каталог 0700); список кошельков с именами и адресами — без секретов;
- разблокированный кошелёк существует только в памяти процесса и
  блокируется через 10 минут без использования;
- все `/v2/desktop/*` требуют заголовок `X-Orvexa-Session` со случайным
  токеном, который создаётся при каждом запуске и передаётся только окну
  приложения (initialization script WebView); вкладка браузера и другие
  локальные процессы его не имеют (ответ 401);
- показ фразы и экспорт ключа просмотра требуют пароль повторно.

**Создание кошелька:** 24 слова показываются один раз → пользователь
подтверждает 3 случайно выбранных слова → задаёт пароль (≥ 12 символов) →
только после этого seed шифруется и записывается. Восстановление — по фразе.

**Локальная сеть:** создаётся кнопкой; genesis отдаёт 1 000 000 тестовых
атомов выбранному кошельку, соль случайная (у каждой сети свой chain ID).
Встроенный узел — единственный валидатор этой сети (ключ
`<данные>/v2/node/validator.key`): блок решается, когда есть переводы, не
чаще раза в 2 с; данные в `<данные>/v2/node`. Сеть старого формата (один
производитель, профиль версии 1) при запуске переносится в
`<данные>/v2/retired-<время>`; кошельки остаются.

**Адреса:** bech32m с префиксом `ovxt` (тестовая сеть), контрольная сумма
ловит опечатки.

Возможности: баланс и ожидающие суммы, новые несвязываемые адреса, приватный
перевод, публичный платёж с явным подтверждением раскрываемого, история с
квитанциями, проверка квитанции, показ фразы, экспорт ключа просмотра (полный /
только входящие, с описанием охвата), кошелёк только для просмотра (на время
сессии), обозреватель v2.

## 6.6. Профиль сети и подключение одной кнопкой

Файл `orvexa-v2-network` версии 2 (JSON, публичный) описывает сеть: имя,
chain ID, соль, эмиссию, `anchor_window`, `max_expiry_delta`, валидаторов
(`{key, url}`: открытый ключ и адрес узла для сообщений консенсуса, по
возрастанию ключа), genesis (hex) и до 16 адресов публичных узлов
(`https://…`). Приложение не доверяет файлу на слово: оно проверяет
доказательство и подписи genesis и пересчитывает chain ID из параметров.
Адреса узлов и валидаторов в chain ID не входят — их можно менять, не меняя
сеть; ключи валидаторов входят. Версия 1 (один производитель) не принимается.

«Подключиться» в Desktop: файл сохраняется в `<данные>/v2/network.json`,
встроенный узел становится **ведомым** первого публичного узла (или узла
валидатора). Он скачивает каждый блок, проверяет сертификат коммита, правила
и доказательства и только потом сохраняет. Переводы пересылаются этому узлу.
Если на компьютере лежит ключ одного из валидаторов сети
(`<данные>/v2/node/validator.key`), узел работает валидатором. Если сборка содержит опубликованный профиль
(`crates/orvexa-shielded/networks/default.json`), в приложении появляется
кнопка «Подключиться к тестовой сети ORVEXA v2» без выбора файла.

### 6.6.1. Список сетей и подключение без файлов

Публичные сети перечислены в `docs/networks/directory.json` (формат
`orvexa-v2-directory` v1: `issued_at`, `expires_at`, профили сетей, первая —
рекомендуемая) с подписью `directory.json.sig`: Ed25519 над
`"ORVEXA/v2-network-directory/v1\n" ‖ байты файла` ключом выпуска, которому
приложение уже доверяет для обновлений ([UPDATES.md](UPDATES.md)). GitHub Pages
отдаёт их по `https://waxiechc.github.io/orvexa/networks/directory.json`.

Кнопка «Подключиться к сети ORVEXA v2» скачивает список только по нажатию,
проверяет подпись, срок (по умолчанию 90 дней), каждый профиль полностью
(genesis, chain ID, валидаторы) и наличие публичного узла. Если сеть одна,
приложение сразу подключается к ней; если несколько — показывает выбор. Чужая
подпись, правка после подписи, просроченный список или сеть с неверным
genesis отвергаются. Подписывает список `orvexa-v2-node directory --key
<ключ выпуска> --profile network.json --out docs/networks/directory.json`.

### 6.6.2. Рекомендованная комиссия

Правило кошелька и узла, не реестра (реестр требует лишь ≥ 1 атома):
`fee = 5 × max(actions, 2) × k`, где `k` = 1, 2 или 4 при очереди до 49,
50–199 и от 200 ожидающих переводов. Узел сообщает условия на `GET /v2/fee`
(ведомый спрашивает узел, которому пересылает переводы). Кошелёк выбирает
notes так же, как при отправке, считает число actions и подбирает комиссию,
которая покрывает и саму себя. В приложении комиссия подставляется сама по
мере ввода суммы; её можно поменять вручную и вернуть рекомендованную.
Обычный перевод (2 actions) стоит 10 атомов.

### 6.6.3. v2 — основной кошелёк приложения

В окне ORVEXA Desktop приватный кошелёк v2 открывается первым. Тестовая сеть
v1 там заморожена: обзор, история, обозреватель, кошельки, резервные копии и
узел v1 доступны только для просмотра, отправка и получение v1 закрыты.
Протокол v1, его узел и веб-кошелёк в браузере не менялись; балансы v1 в v2 не
переносятся — v2 начинается со своей эмиссии.

## 6.7. Несколько валидаторов: консенсус BFT (этап 8)

Блоки решает Tendermint BFT в реализации Malachite
(`arc-malachitebft-core-consensus` =0.8.1, Circle, Apache-2.0). Это конечный
автомат без сети и ввода-вывода; узел (`crates/orvexa-shielded/src/bft`) сам
подписывает, проверяет, ведёт таймеры, журнал и рассылку. Сценарии отказов
сначала проверены на детерминированном симуляторе
([research/bft-eval](../research/bft-eval/README.md)).

- **Гарантии** при n = 3f + 1 валидаторах с равными голосами: честные
  валидаторы никогда не принимают разные блоки на одной высоте при любом
  поведении сети и не больше f нечестных; блоки идут, пока больше 2/3
  валидаторов на связи. Без кворума сеть стоит, а не расходится.
- **Значение консенсуса** — block ID (`ProposalAndParts`). Предлагающий
  раунда (по кругу: (height − 1 + round) mod n) рассылает тело блока
  отдельно; каждый валидатор проверяет его полными правилами §4 (с
  доказательствами) и только потом сообщает «допустим / недопустим».
  Расширения голосов выключены.
- **Подписи.** Голоса — байты precommit/prevote из §6 (prevote с 0x00, nil —
  0x00 вместо block ID); предложения — `"ORVEXA/shielded-proposal/v2\n" ‖
  chain_id ‖ height ‖ round ‖ pol_round ‖ block_id ‖ ключ`. Все подписи
  консенсуса проверяются `verify_strict`, как в реестре, поэтому голос,
  принятый консенсусом, не может дать сертификат, который отвергнет реестр.
- **Сеть.** Валидаторы шлют друг другу сообщения `POST /v2/consensus`
  (двоичный формат `OVXC` v1: голос, предложение, сертификаты polka и раунда,
  тело блока) по адресам из профиля. Переводы, принятые валидатором,
  пересылаются остальным валидаторам.
- **Журнал (WAL)** — `consensus.sqlite` рядом с базой (`synchronous=FULL`):
  входы консенсуса по высотам, тела блоков текущей высоты и свои предложения.
  Запись на диске раньше, чем голос уходит в сеть; после перезапуска на ту же
  (высоту, раунд) предлагается тот же блок; записи уже принятых высот не
  воспроизводятся как следующая высота (эту ошибку нашёл симулятор).
- **Отставание.** Валидатор раз в секунду спрашивает соседей о высоте и
  забирает недостающие блоки с сертификатами, как ведомый.
- **Без работы сеть молчит**: высота начинается, когда в мемпуле есть перевод,
  когда журнал показывает незаконченную высоту или когда сосед уже голосует.
  Блок может оказаться пустым, если предлагающий ещё не получил перевод.
- **Таймауты** по умолчанию: предложение 1,5 с (+0,5 с за раунд), prevote и
  precommit 0,5 с (+0,25 с), повторная рассылка 3 с.

Оговорка: Malachite помечен как alpha и не проходил внешний аудит. Для
тестовой сети этого достаточно; перед реальными средствами нужен внешний
аудит движка или переход на проверенный (CometBFT).

## 9. Не охвачено и открыто для review

- **P3-08** (комиссия больше остатка эмиссии) проверяется кодом, но честно
  такую транзакцию не построить: комиссия равна value balance и ограничена
  входами. Отдельного теста нет.
- **Отключение питания.** Аварии проверены остановкой процесса, а не
  выключением ОС; это опирается на гарантии SQLite при `synchronous=FULL`.
- **Приложение.** v2 в Desktop — только локальная сеть на одном компьютере:
  подключения к чужому узлу v2 из интерфейса нет. Узлы v2 связаны по HTTP,
  а не через P2P v1; ведомые не раздают блоки другим. Кошельки только для просмотра не
  сохраняются между запусками. Окно приложения на Windows с v2 не проверялось.
- **Метаданные:** запрос txid у обозревателя может связать посетителя с
  платежом; IP и время отправки не скрываются.
- **Консенсус (§6.7).** Движок без внешнего аудита. Набор валидаторов
  постоянный (смена — новая сеть), голоса равные, наград и наказаний нет;
  доказательства двойного голосования только пишутся в лог. Каналы между
  валидаторами не аутентифицированы (голоса подписаны, тела блоков привязаны
  к подписанному предложению, но посторонний может слать мусор — он
  отбрасывается после проверки). Тест на процессах — одна машина, без
  настоящих задержек сети.
- **Mempool** не сохраняется: если упали все валидаторы, ожидающий перевод
  надо отправить снова (тот же txid).
- **Детерминированные векторы.** Builder использует ОС-случайность, поэтому
  побайтных фиксированных векторов транзакций пока нет. Нужен режим с заданным
  RNG только для тестов.
- **Кошелёк:** birthday > 0 (начало скана не с genesis) требует frontier дерева
  на высоте birthday; пока сканирование всегда с genesis. Passphrase BIP39 не
  поддерживается. Состояние скана не сохраняется на диск: после открытия файла
  кошелёк пересканирует цепочку. Автоблокировка — задача интерфейса.
- Дерево узла в прототипе помечает все листья ради старых тестов; seed-кошелёк
  его уже не использует.
- **Раскрытие:** отчёт о балансе на выбранной высоте не реализован. Квитанция
  не доказывает, кто отправитель; доказательство авторства платежа требует
  отдельной подписи и анализа. Формат квитанции ORVEXA-специфичен: стандарта
  раскрытия для Orchard (аналога ZIP 311 для Sapling) нет.
- **Сетевые метаданные:** IP и время отправки этим уровнем не скрываются.
- **P1-02:** публичного отчёта аудита circuit не найдено (см. §10).

## 10. Решение по библиотеке (P1-07)

**Принято владельцем проекта 2026-10-18: `orchard 0.16.0`, Ironwood v3 /
PostNu6_3, для тестовой сети v2 на условиях ниже.** Решение не распространяется
на реальные средства.

Почему go:
- Нужные свойства прототип получает только из upstream: скрытые суммы и связи,
  nullifiers, проверка proof и подписей. Собственной криптографии нет.
- Все отрицательные сценарии P2/P3 отвергаются на уровне реестра.
- Ресурсы для desktop приемлемы: доказательство ≈ 0,3 с на action, проверка —
  миллисекунды (Apple M4).
- Лицензии разрешительные, RustSec чист.

Риски и условия:
- В старом circuit Orchard была критическая ошибка soundness
  ([GHSA-ww9q-8r59-xv46](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-ww9q-8r59-xv46),
  исправлено в NU6.2, [ZIP 257](https://zips.z.cash/zip-0257)). Поэтому
  принимается только `PostNu6_3`, без fallback на старые ключи.
- Для Ironwood заявлена формальная верификация knowledge soundness / balance
  integrity на Lean ([zcash/ironwood](https://github.com/zcash/ironwood)).
  Её авторы прямо исключают ошибки реализации. Публичного отчёта по аудиту
  circuit от zkSecurity найти не удалось. Это сведения из заявки самих
  исполнителей, а не независимого отчёта.
- Сравнение с Monero (P1-06) не проводилось. Это неизвестное, а не преимущество Orchard.
- Перед любыми реальными средствами нужен независимый аудит точной реализации
  ORVEXA: конверта, правил реестра, хранения и кошелька.
